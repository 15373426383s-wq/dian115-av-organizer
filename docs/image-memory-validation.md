# 图片内存优化验证（1.2.2）

日期：2026-10-31。宿主 API 仍为 3.5；完整优化需要本轮宿主代码，未部署到运行服务器。

## 实现

- 插件新配置默认最大宽度 1200；2:3 海报约 1200×1800。小图不放大，已有显式 0 继续保留原尺寸，原始文件不覆盖。
- 宿主 `inspect` 只读图片头或 SVG 尺寸，JPEG 方向信息与正式解码使用同一个解析器；不再为获取尺寸展开全部像素。
- 裁剪只选择原图区域，不产生整张裁剪副本；按输出尺寸生成画布后再叠加水印，多张水印复用画布。
- 不透明 JPEG 不做白底合成；透明 RGBA/NRGBA 就地合成白色，保留正确透明度与颜色。
- 处理中源图像素累计最多 24 MP；大图在解码前排队。现有 API 最多两个请求的限制不变，取消或失败会释放额度。
- 头部检查不证明像素完整，实际处理失败仍会切换候选图片。

## 内存对比

本机 Go 测试使用宿主真实图片函数、合成 JPEG、相同比例 2:3、质量 92，同时提交两个请求。旧数据来自优化前一次采样；优化后每个场景运行三次，下表为三次峰值范围。测量的是每 1 毫秒采样的 Go 堆增量（MiB），不是容器 RSS，也不含预先准备好的输入 JPEG 字节。大图提交后会按新预算排队，因此并非一直同时解码两张。

| 输入尺寸（两张） | 优化前，原尺寸输出 | 优化后，原尺寸输出 | 优化后，默认最大宽 1200 |
| --- | ---: | ---: | ---: |
| 1200×1800 | 55.96 | 8.73 | 8.48–8.73 |
| 3000×4500 | 387.32 | 46.92–46.94 | 80.03–80.04 |
| 4000×6000 | 622.70 | 50.35–84.75 | 74.94–75.48 |

本样本本身已经是海报比例，且不带水印、透明度或旋转。原尺寸 JPEG 可以直接编码解码后的像素；缩放则需要重采样缓冲，所以“缩小输出”不一定比优化后的原尺寸路径更省峰值内存。减少整图副本和大图排队是本轮主要收益；缩小画布还减少后续水印处理和输出体积。

首次解码仍展开原图；不提供 JPEG 缩略解码。人脸检测、大型水印、透明 PNG、EXIF 旋转、实际文件读取与其他宿主任务均可能增加峰值。回收时机不同会导致采样峰值波动，不能把上述结果当作整个宿主的内存上限。

## 正确性检查

插件完整回归 264 项与页面冒烟检查通过。宿主测试覆盖：大小端 EXIF 1–8 的尺寸一致性与缩放、截断/损坏 EXIF、仅有头部但无像素的文件、SVG 尺寸、原图区域引用、裁剪位置、半透明水印叠加、透明像素白底、像素预算等待/取消/失败释放。宿主 Linux 基线构建通过。

没有移动用户媒体、下载影片、发送 AI 请求或向 115、PT、Emby 写入数据。测试只使用临时生成的图片与隔离测试环境。
